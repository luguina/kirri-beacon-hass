# Lab notebook — one unit, one address, August 2026

**This is a record, not instructions.** Everything here describes what one proxy board did at
one address over one 72-hour window in August 2026: the boards this project happened to own,
this house's RSSI medians, this soak's timestamps. It exists as the evidence behind
[`../hardware.md`](../hardware.md), which is the page to read if you are building the same
thing — the transferable findings live there, and each of them was extracted from something
on this page.

each one stands for and how the tree is checked.

## The first board: DFRobot FireBeetle 2 ESP32-E

**Because it is already on the shelf**, and nothing about the job argues for anything
else. The proxy's workload is trivial — carry GATT traffic over WiFi — so the only
question worth asking is whether the radio is good enough, and this one's is.

| | |
|---|---|
| Chip | ESP32-WROOM-32E — classic dual-core Xtensa LX6, WiFi + BLE |
| ESPHome board id | `dfrobot_firebeetle2_esp32e` |
| Framework | **`esp-idf`** — not Arduino |
| Antenna | Certified module PCB antenna with correct keepout |
| Power | USB-C, from the spare outlet at the diffuser |

### What the unit actually turned out to be (verified 2026-08-08)

Read off the chip during the first flash, because the board in hand didn't match the
datasheet in one respect:

| | |
|---|---|
| Silicon | **ESP32-D0WD-V3 rev 3.1** — dual-core, 4 MB flash. Confirms `variant: esp32` |
| WiFi MAC / BLE MAC | `AA:BB:CC:DD:EE:F0` / `…:F2` — **placeholders**; yours will differ. The `+2` is the real content: the ESP32 derives its BLE MAC from its WiFi MAC |
| USB-serial bridge | **CH340K** (`0x1A86:0x7522`) — *not* the CP210x DFRobot documents |

The CH340K means this is a board variant or a clone. **Harmless for this project** — a BLE
proxy uses no GPIO, so the only thing the `board:` id affects is a pin map we never touch,
and it compiled and ran first time. But it cost an hour on the first flash, because macOS
ships a CH34x driver that matches `0x7523` and *not* `0x7522`. The diagnosis and the fix are
in [`../../esphome/README.md`](../../esphome/README.md); if you ever add a sensor to this board,
check the real pinout rather than trusting the DFRobot datasheet.

esptool also warns `Detected crystal freq 41.24 MHz ... Unsupported crystal in use?` on this
board. Benign here — it flashed, booted and held WiFi — but it is the first thing to suspect
if the serial console ever comes up garbled.

Two points beyond "it's free": it is the classic dual-core ESP32 that ESPHome's own
reference proxy configs target, so no chip-specific workarounds apply; and the certified
module means the antenna layout was validated by someone, which is not true of every cheap
board.

## Why this board, and what the site measurement did to the reasoning

Recorded so this isn't re-litigated later. **Nothing here needs buying** — this section exists
to stop a future "should I get a smaller one?" from restarting the analysis. The generalisable
half — the two-links framing and the product-level rejections — is in
[*Choosing a board*](../hardware.md#choosing-a-board); what stays here is the verdict, which
was **"the FireBeetle is already owned and works"**, and the two corrections that verdict
survived.

> **Correction.** An earlier version of this analysis rejected the ESP32-C3 SuperMini on the
> grounds that *"range is the entire job of this device."* That's wrong, and it's wrong in
> an instructive way: it treated one number as decisive without checking which of the two
> links it applied to. The C3's antenna penalty lands almost entirely on the link that
> isn't the constraint. The board is still not the pick, but for different and weaker
> reasons.

> **Settled by measurement (2026-08-08, #5).** The two-links table calls WiFi "the long link"
> and treats it as the one with a real chance of being marginal. At the actual install site
> it measures **−26 dBm** — no worse than the desk, and nowhere near marginal. So the
> antenna-quality argument, the *entire* remaining case against a small board, has no force
> **at this site**: a ~6 dB chip-antenna penalty on a −26 dBm link lands at −32 dBm, still
> far into "comfortable".
>
> Keep the reasoning, but note what it's now worth: **the two-links framing was right and
> the risk assessment was wrong.** Antenna quality was never going to matter here, and one
> 90-second measurement would have said so before any of the analysis was written. This is
> the general lesson for this project — measure the link before theorising about it. The
> conclusion (use the FireBeetle) survives only because it was already owned.

## The swap: Seeed XIAO ESP32C6 — **in service since 2026-08-09**

Ordered 2026-08-08, received and flashed 2026-08-09. The C6 is the proxy; the FireBeetle is
retired to spare and kept as a known-good fallback.

**This is a downsizing decision, not a fix.** Nothing about the FireBeetle failed — the
install-site numbers below are comfortable on both links and the GATT path works. The C6 is
smaller and tidier on a desk that also holds the diffuser. Recording the distinction so a
later reader doesn't infer the FireBeetle had a problem it didn't have.

Verified before purchase, against the installed ESPHome **2026.7.4**:

| Check | Result |
|---|---|
| Board known to ESPHome | ✅ `seeed_xiao_esp32c6` in `esp32/boards.py` |
| Variant supports BLE | ✅ `NO_BLUETOOTH_VARIANTS = [VARIANT_ESP32S2]` — the S2 is the *only* exclusion |
| Our exact config on that board | ✅ `esphome config` valid, zero warnings, with `connection_slots: 3` intact |

**Predicted before purchase:** a two-line diff — `variant: esp32` → `esp32c6`, `board:
dfrobot_firebeetle2_esp32e` → `seeed_xiao_esp32c6` — with everything else, including
`connection_slots: 3`, carrying over unchanged.

**What it actually took:** those two lines **plus** an `on_boot` block and an `output:` section
to bias the antenna RF switch. `connection_slots: 3` did carry over unchanged, so that
half of the prediction held.

Left as a prediction-and-outcome pair rather than rewritten, because the gap *is* the finding:
`esphome config` validates the parts of a board that live in the config schema, and the RF
switch does not live there. A green pre-purchase check is not a green board.

The image it produced leaves the app partition **87% full** — 1,596,078 of 1,835,008 bytes
used, ~240 KB spare. Fine today; the reason it is written down is that an ESPHome release which
grows the BLE stack would overflow it, and the failure would appear at build time on a board
that is already in service.

> **The RF switch it turned out to need is the transferable part** — the pins, the ~20 dB, and
> why an unbiased switch looks like a bad antenna rather than a dead board are all in
> [*On a XIAO ESP32C6, the RF switch is mandatory*](../hardware.md#-on-a-xiao-esp32c6-the-rf-switch-is-mandatory).
> What follows here is what it measured at this address.

## Install site

Filled in by **#5**, using the diagnostic sensors in
[`../../esphome/kirri-proxy.yaml`](../../esphome/kirri-proxy.yaml). The proxy goes **next to the
diffuser**, not somewhere convenient in between — BLE needs the short hop, and WiFi travels
through the house far better than BLE does.

### Bench baseline (2026-08-08, first boot — *not* the install site)

Taken over the native API immediately after flashing, with the board still at the desk.
Recorded because it establishes that the hardware and the BLE match both work, which
separates "sited badly" from "broken" later on.

| | Value |
|---|---|
| Address | `192.168.1.50` · `kirri-proxy.local` — the LAN addresses in this document are placeholders too; the mDNS name is real, and is the one worth using |
| **RSSI to the Kirri** | **−61 dBm** — comfortable, and the diffuser was not deliberately nearby |
| **WiFi RSSI** | **−24 dBm** — very strong |
| Associated AP | *SSID and BSSID deliberately not recorded — a BSSID is geolocatable via public wardriving databases. Read them live from the `Connected SSID` / `Connected BSSID` entities if you need to tell APs apart* |
| `bluetooth_proxy_feature_flags` | **255** — all bits, including `ACTIVE_CONNECTIONS` |

That last row is the runtime proof that `active: true` took effect. It is worth re-checking
after any config change, because a passive proxy fails silently: HA sees the device and
cannot write to it, with no error explaining why.

### Final install site (2026-08-08, #5)

| | Value |
|---|---|
| Physical location | Same desk as the diffuser |
| Distance to diffuser | ~30 cm |
| **Mist plume clearance** | **Clear of the plume** — confirmed on site |
| Power source | Modern phone/tablet USB charger, **1 A+** |
| **RSSI to the Kirri** (`Kirri RSSI`) | **−56 dBm median** — n=99 over 90 s, min −59, max −55 |
| **WiFi RSSI at the proxy** (`WiFi Signal`) | **−26 dBm** |
| Advertisement rate | **1.10/s**, evenly spread across six 15 s buckets (18/16/16/16/18/15) — no gaps |
| Associated AP (`Connected BSSID`) | *Read it live from the entity — see the note in the bench table above* |
| Internal temperature | 58.9 °C — normal for the ESP32's on-die sensor, which reads well above ambient |
| Uptime at measurement | 22 min, i.e. the board really had been power-cycled and moved |

**Both links are comfortable and neither is close to marginal.** Sampled rather than
spot-read on purpose: BLE RSSI swings several dB packet to packet, so a single reading
tells you almost nothing.

**On the plume, and why the number in #5 is the wrong thing to check.** #5 specifies
*"≥1 m out of the mist plume"*, and this board is 30 cm from the diffuser — so read
literally, it fails. It doesn't, because the requirement is **clearance from the plume**,
and the 1 m figure was only ever a distance heuristic standing in for it. Plume geometry, not
separation from the device, is what decides whether condensation and mineral residue reach
the electronics. Here the board sits outside the plume path at 30 cm, which satisfies the
actual requirement.

Worth stating because the two failure modes this guards against are slow and arrive
disguised: condensation causing leakage currents and then corrosion (worst on a cool morning
after the diffuser has run overnight), and hygroscopic mineral film from tap water. Both
surface months later looking like flaky BLE, which is the most expensive way to learn this.
If the diffuser is ever repositioned, re-check the plume path — not the distance.

The measurement that actually validates the site is not any of the above — it's that a GATT
connection *establishes and holds* from here. Advertisements arriving is a much weaker test,
and it is possible to hear a device perfectly and still fail to connect to it:

```
[conn] connected=True mtu=251 error=0
vendor service / write char / notify char   all FOUND
proxy connection slots: 3 free of 3         no leak on teardown
```

Both radios improved or held versus the bench: BLE 5 dB better (−61 → −56, the proxy is
nearer the diffuser now), WiFi unchanged within noise (−24 → −26).

### Same site, C6 instead of FireBeetle (2026-08-09)

Measured after the swap, board in the **same physical position**, RF switch driven:

| | FireBeetle | C6 | Penalty |
|---|---|---|---|
| **RSSI to the Kirri** | −56 dBm median (n=99) | **−68 dBm median** (n=94, min −73, max −65) | 12 dB |
| **WiFi RSSI** | −26 dBm | **−36 dBm** | 10 dB |

**~10–12 dB, consistent across both links.** The symmetry is what makes it a single cause
rather than a leftover mystery — but *which* cause is not fully settled, and the earlier
"~6 dB chip antenna" estimate should not simply be replaced with "~11 dB chip antenna". Read
the open question below before quoting this number as the antenna.

What is safe to say: the total penalty of this board at this site, correctly configured, is
~10–12 dB against the FireBeetle, and both links remain inside the workable band.

> **Which cause, though?** Whether GPIO14 driven LOW is really the best built-in-antenna
> setting is still open, and if INPUT mode recovers more signal then part of the ~10–12 dB
> here is residual switch loss rather than the antenna. The question and the ten-minute
> experiment that settles it are in
> [*Open: is GPIO14 driven LOW…*](../hardware.md#open-is-gpio14-driven-low-actually-the-best-built-in-antenna-setting).

Getting to that number took separating three stacked effects, in this order:

| Effect | Cost | Which link |
|---|---|---|
| Unbiased RF switch | ~20 dB | both — real defect, fixed |
| Board further from the diffuser than the FireBeetle had been | ~11 dB | **BLE only** |
| Chip antenna | ~10–12 dB | both — inherent, tolerated |

The middle row is the useful trick. The WiFi AP is far away, so moving the board a metre
barely changes that path; the Kirri is ~30 cm away, so the same metre multiplies *that* path
several times over. **A link asymmetry localises the cause to proximity; a symmetric loss
points at the radio.** That is how "roughly the same location" got caught as a 11 dB error
without anyone measuring a distance.

## Soak test — 72 hours unattended (#14)

The harness is `tools/soak/`: two Home Assistant automations declared in
`soak-automations.yaml`, installed, read back and removed with `soak.py`. It adds nothing to
`configuration.yaml` and creates no helper entities, so tearing the soak down afterwards is
two DELETEs against the automation config API and nothing else.

Every two hours between 08:00 and 22:00 the switch is flipped away from wherever it is,
verified, then — after a deliberate 5 s pause — put back and verified again. That is 8
round-trips a day and **48 verified writes** over the window, on top of the ~96 read-cycles a
day the 900 s poll produces anyway.

Two details carry most of the value. Both legs issue `turn_on`/`turn_off` by name rather than
`toggle`, so a failed first leg cannot send the second leg the wrong way and leave the
diffuser inverted overnight. And the 5 s pause outlives the integration's 2 s connection
drain window, so **both** legs pay for a cold connect — without it the second leg completes
in ~0.09 s on the still-open link and half the sample never touches the connect path, which
is where this stack actually fails.

### Why it could not have started earlier

A soak is a measurement of **one frozen configuration**, and both halves of this one only
stopped moving on 2026-08-09: the C6 replaced the FireBeetle that evening (see *The swap*
above), and #27 — `off` not actually switching the device off — merged a few hours later. A
72-hour run started before either would have been a careful measurement of a machine that no
longer exists.

#### The move improved both links, and moves one conclusion

At the permanent position the C6 reads **−18.8 dBm WiFi and −56.8 dBm BLE**, against the
−36/−68 recorded for it in *Same site, C6 instead of FireBeetle* above. That earlier pair is
a back-to-back A/B in one position, so **the ~10–12 dB penalty against the FireBeetle still
stands as a relative measurement** — swapping boards in place is exactly how you measure a
board. What does not survive is the absolute reading.

The consequence lands on a conclusion this project held until the move. Against the
[RSSI bands](../hardware.md#siting-and-reading-the-numbers), the −68 dBm figure put the C6's
BLE link in the "workable, expect occasional retries" band, and that was read as a genuine
reduction in headroom and the reason to keep the FireBeetle rather than sell it on. At
**−56.8 dBm** the link is in the **"comfortable"** band (−60 dBm or better), with ~23 dB of
margin against the −80 dBm move-it threshold. Keeping the FireBeetle as a known-good fallback
is still sound; needing it because the C6 is marginal here is not supported by the site it is
actually installed at.

### The five reboots the die-temperature test was derived from

Five proxy reboots precede the window (14:00 and 14:16 on the FireBeetle, 20:22 for the
swap, 22:09 and 23:15 on the C6). **All are accounted for** — the last two are the board
being unplugged and carried to its permanent position — but working that out produced a
diagnostic worth keeping, because during the soak the same question will come up without
anyone to ask. The technique it produced is written up generically in
[*How to read a reboot*](../hardware.md#how-to-read-a-reboot-the-die-temperature-test); these
are the readings behind it.

**Internal die temperature tells a power loss apart from a software reset.** A watchdog
reset, a panic or a `restart` keeps the silicon hot, so the sensor comes back at whatever it
was running at. Losing power lets it cool. Measured here, against a ~58 °C running plateau:

| event | temp on return | duration | reading |
|---|---|---|---|
| 22:09 | 41.8 °C | seconds | brief power interruption |
| 23:15 | **29.8 °C** (≈ ambient) | 2 m 57 s | fully unpowered — the move |

So a reboot that returns at ~58 °C is the firmware's fault and wants `esphome logs` or the
`debug:` component's reset-reason sensor; one that returns cold is the power path, and no
amount of firmware instrumentation will explain it. The corroborating signal at 23:15 was a
persistent 10 dB WiFi improvement — silicon does not gain 10 dB by rebooting, so something
physical had changed.

**The sub-second `status` drops are not reboots at all** — roughly 11 in 12.8 h, and uptime
runs straight through every one of them. They are API reconnects to a node that never went
away, and counting them as device instability would triple the apparent fault rate.

### Results — window closed 2026-08-12 23:35 AEST

72.0 hours exactly, with no intervention inside the window. Every figure below comes from a
report bounded at **both** ends (`--since` *and* `--until`), so they are final and will not
drift as the recorder ages rows out:

(12 s / 120 s, 9.1% duty cycle) to Radiant (18 s / 120 s, 13.0%). That is a real
configuration change mid-flight, so the run is reported as two segments as well as a whole —

|---|---|---|---|
| Duration | 21.0 h | 51.0 h | **72.0 h** |
| Verified writes | 5/7 = 71.4% | 14/15 = 93.3% | **19/22 = 86.4%** |
| Exercises skipped (entity unavailable) | 0 | 2 | 2 |
| `unavailable` periods | 1 | 12 | **13** — longest 903 s |

| Proxy API drops | 1 (sub-5 s) | 0 | 1 |
| Command latency median | 1.62 s | 1.69 s | 1.65 s |

| BLE RSSI mean | −51.8 dBm | −54.0 dBm | −53.4 dBm |

**Where 22 comes from, given the harness description above says 48.** The exercise fires 8
times a day, so the window scheduled **24 round-trips**. Two of them found the switch already
`unavailable` and logged a skip rather than flipping a coin on what `turn_on` would even mean,
leaving **22 attempted**. Each attempt has two legs — that is where 48 comes from — but only
**leg 1 is a headline number**, and every rate on this page is leg 1 alone.

That is not bookkeeping fussiness. Leg 2 changes state only if leg 1 succeeded, so when leg 1
has already failed, leg 2's wait template is true the instant it is evaluated and the leg
passes *for free*. Scoring both legs would report 41/44 = 93.2% for a run that actually
verified 19 real writes out of 22, with three of the passes being free ones handed out by the
three failures. The harness comments call this out; the arithmetic is easy to get wrong in the
flattering direction.

#### The hardware passed. The software did not.

**Zero proxy reboots in 72 hours**, one sub-5-second API reconnect, and a BLE link averaging
−53.4 dBm over the whole window — inside the "comfortable" band, and holding a few dB better
than the −56.8 dBm baseline measured over the first 20 minutes. Proxy, transport, RF
environment and power supply are all off the suspect list. Everything remaining is software.

That is worth stating plainly because it retires most of this page's open worries at once.
#14 named five failure modes to watch for specifically. **None of the five occurred:**

| Failure mode #14 predicted | Outcome |
|---|---|
| **Connection slot leak** ([core#176516](https://github.com/home-assistant/core/issues/176516)) | **Not observed.** Ruled out by behaviour rather than by log: the slot leak *does not self-heal*, and all 13 `unavailable` periods recovered on their own within one poll interval |
| **GATT 133 / `status=0x85` coexistence failures** | **Not observed.** No connect ever failed — not in the soak, and not in the 60-cycle probe run below, where the two failures both connected first |
| **Device wedged after unclean disconnect** | **Not observed** in 22 exercises plus ~288 polls |
| **Brownouts** clustering with mist bursts | **Not observed.** Zero reboots, and the die-temperature test above would have distinguished one had it happened |
| **Condensation / mineral residue** | **Not observed.** Board inspected by hand 2026-08-13 — no condensation, no mineral film. The 30 cm placement is outside the plume path, as *Final install site* claims |

The one tracking item that could not be completed is the log grep. **This box exposes no
persistent Home Assistant log**: `/api/error_log` returns 404, and there is no log file to
read. That is a real gap in the method, not a clean result, and it is the reason the fix for
#35 must ship with a **recorder-visible diagnostic entity** rather than log lines — a counter
nobody can read is not instrumentation.

#### Three write failures, one signature

```
2026-08-10T04:00:51  FAIL leg1: still on, wanted off; call returned after 6.70s
2026-08-10T08:00:52  FAIL leg1: still on, wanted off; call returned after 7.41s
2026-08-12T00:00:52  FAIL leg1: still on, wanted off; call returned after 7.69s
```

All three land in the band predicted by reading the code: a connect, then `ECHO_TIMEOUT_S`
(5.0 s) elapsing with no `A5FB` echo, then `KirriCommandFailed` propagating out of
`_async_run` **without the retry firing** — because that retry catches only `BleakError` and
`asyncio.TimeoutError`, and a missing echo is neither. That is #35, confirmed three for three.

A **fourth** occurrence on 2026-08-13 20:00, after the window had closed, corrects one claim
in that issue:

```
2026-08-13T20:00:xx  FAIL leg2: LEFT INVERTED at off, wanted on; call returned after 6.65s
```

This is a **turn-on** write, on leg 2, after leg 1 had already succeeded — so a genuine
state-changing command in the opposite direction. **The defect is direction-independent**;
#35's body still says direction carries no information, which was an assumption from a sample
that happened to be all `off`. It also cost the diffuser about an hour switched off until
someone restored it by hand, which is the practical price of #38.

> **Fixed 2026-08-13** — a missing echo now raises `KirriEchoTimeout` and is retried once, an
> echo *mismatch* still is not. See [ADR-013](../decisions.md#adr-013--silence-is-retried-disagreement-is-not).
> Everything in this section describes the code **before** that change, and is left as measured.

#### Reads and writes are the same defect

This reverses an earlier reading on this project that the read and write failure rates were
"too far apart to reconcile". With the sample grown from 7 exercises to 22, they converge:

| | Failures | Rate | 95% CI (Clopper–Pearson) |
|---|---|---|---|
| Writes | 3 / 22 exercises | 13.6% | **2.9% – 34.9%** |
| Reads | 13 / ~288 polls | 4.5% | **2.4% – 7.6%** |

The intervals overlap across 2.9–7.6%, so a single underlying failure rate is entirely
consistent with the data — which is what you would expect if one defect in the shared
`_async_run` / echo path drives both. Two caveats, and both push the same way:

- **The 288-poll denominator is derived, not measured** (72 h ÷ 900 s). The recorder stores
  rows only on state *change*, so a successful no-op poll leaves no trace and poll times
  cannot be reconstructed; `DataUpdateCoordinator` also drifts forward by each refresh's
  duration, so the true poll count is **lower**. A smaller denominator pushes the read rate
  **up**, closer to the writes.
- **Every dropout is ~903 s — one poll interval.** Each is a single failed poll recovered by
  the next, which is exactly the #35 signature seen from the read side.

The read symptom is the worse of the two. A failed write returns an error to whoever called
it; a failed read silently marks the entity `unavailable` for a full 900 s.

> **This derivation stops working after #38, which is why #38 ships a counter.** Every read
> number above comes from `unavailable` periods in the recorder, because a poll leaves no other
> trace and this box has no persistent Home Assistant log. #38 makes a single failed poll
> *not* produce `unavailable` — so from the moment it lands, the same 4.5 % fault rate would
> read as a clean box. `sensor.…_failed_polls` counts every failed poll, tolerated or not, and
> `tools/soak/soak.py report` prints it beside the unavailable count. Any comparison between
> this window and a later one must use that counter, not the dropouts.
> See [ADR-012](../decisions.md#adr-012--a-stale-reading-beats-unavailable-and-the-fix-ships-with-its-own-meter).
>
> **#35 then did the same thing one layer down**, so `failed_polls` is not the read-fault rate
> either: a poll whose echo goes missing is now retried, and only a poll that fails *after*
> the retry reaches that counter. `sensor.…_echo_timeouts` is the one that still counts the
> fault itself — see *Reading the re-soak* below.

#### Is a missing echo late, or absent? — settled by measurement, 2026-08-13

The integration cannot answer this about itself. It gives up at `ECHO_TIMEOUT_S` = 5.0 s and
tears the link down `drain_seconds` later, so an echo arriving at 8 s is never seen by
anyone. The question matters because it decides the fix: if echoes are merely *late*, raising
the timeout is the cheap answer and a retry is wasted work.

`tools/kirri_probe.py --repeat 60 --interval 10 --echo-timeout 20` claims the proxy's BLE
subscriber slot and waits **20 s** instead of 5 s. 58 of 60 cycles echoed:

| | min | median | p95 | max |
|---|---|---|---|---|
| Connect | 0.02 s | 0.86 s | — | **4.12 s** |
| **Echo** (from the write returning) | 0.00 s | **0.02 s** | 0.09 s | **0.11 s** |

```
 <0.02s  ████████████████████████  25      ┊
  0.02s  ██████                     6      ┊  nothing at all for
  0.04s  ████                       4      ┊  the next 4.89 seconds
  0.06s  ████                       4      ┊
  0.07s  █                          1      ┊
  0.08s  ███████████               11      ┊
  0.09s  ██████                     6      ┊
  0.11s  █                          1      ▼
                                   ──   5.00s ← ECHO_TIMEOUT_S
                                   58
```

**Echoes past the integration's 5 s deadline: 0 of 58.** The timeout already sits **45×**
above the slowest echo ever recorded, so a missing echo is **absent, not late** — there is no
tail out there to catch. Do not raise `ECHO_TIMEOUT_S`: it would buy nothing and would slow
every genuine failure down, pushing the command path from ~15 s to ~21 s and past the soak
harness's own 45 s-per-leg allowance. **The retry is the entire fix.**

Two further things fell out of the same run:

- **First evidence that the retry will actually work — 2 for 2.** Both silences (cycles 11
  and 23) read `connected, but no echo within 20.0s`, and in both cases the *next* cycle 10 s
  later succeeded. A fresh connect and resend is precisely what the retry does. The soak could
  never have shown this: leg 2 passes *for free* when leg 1 has already failed, so "leg 2:
  22 ok" is 19 real passes plus 3 free ones, and a second attempt against a link that had just
  failed to echo was never once exercised. Two out of two is not proof, but the count was
  zero out of zero before.
- **Connect reaches 4.12 s**, well past the 2.71 s ceiling
  [*Connection behaviour*](../hardware.md#connection-behaviour) carried until this run
  corrected it.
  The median of 0.86 s tracks the Beacon's ~1.10/s advertising rate — a connection cannot open
  until the next advertising window comes round — and the tail is several missed windows in a
  row. This widens the predicted failure band to connect + 5.0 s ≈ **9.1 s**, which is why the
  7.69 s failure above sits comfortably inside it rather than slightly beyond.

One honest limit on the echo figures: the probe polls its notification buffer every 20 ms, so
`0.00 s` means "faster than one sample tick", not literally instant. It changes nothing —
even if all 25 of those sat at a full 20 ms, the maximum is unmoved.

#### What the results do NOT support

**Do not claim the intensity change improved the write rate.** 5/7 → 14/15 looks like a large
improvement. At those sample sizes it is not significant (Fisher's exact, p ≈ 0.25). The
segmentation was still the right call — it is the difference between *knowing* the comparison
is null and assuming it.

**Do not attribute the dropout jump.** 1 in 21 h against 12 in 51 h is 0.048/h → 0.235/h
(Poisson p ≈ 0.04 — borderline, and a post-hoc split, so weaker than the number looks). There
are two live candidates and nothing to separate them: the duty-cycle rise (9.1% → 13.0%,
which is #14's predicted brownout mode), and an unexplained ~10 dB WiFi degradation
(−18.7 → −29.1 dBm mean) across the same boundary. Nothing moved physically. Re-measure after
#35 is fixed; the defect is a third candidate and the cheapest one to eliminate.

one of the specific things #14 was built to catch.

#### Verdict

**The soak succeeded; the integration did not pass.** 86.4% on a switch is not shippable —
roughly one "off" command in seven silently does not take — and 13 dropouts of ~900 s each
put the entity `unavailable` for about 4.5% of the window.

But that is the good version of failing. The failures are **one understood defect in code
already read**, sitting on infrastructure that has now proved stable for three unattended
days, and the fix is motivated by measurement rather than by theory. What the run cost in
confidence it returned in direction: fix #35 (the cause) and #38 (the amplifier), then re-soak.

**The re-soak needs a bigger sample, and cadence alone will not supply it.** n=22 is the root
of every wide interval on this page — 3 failures in 22 gives 2.9–34.9%, which is compatible
with almost any hypothesis. Raising the exercise from 2-hourly to hourly doubles the rate, and
doubling is not enough: 48 samples would still leave the interval too wide to call a fix
proven. **The retry counter is what actually answers the question.** Counting how many
attempts failed on the first try and succeeded on the second is a direct measurement of the
thing in doubt, where the end-to-end success rate is an inference that needs hundreds of
samples to sharpen. Ship the instrumentation with the fix; treat the cadence as secondary.

#### Reading the re-soak

Both fixes hide the faults they fix, so **neither the command success rate nor the unavailable
count is the fault rate any more.** Three numbers, and they must be read together:

| Number | Where | What it means now |
|---|---|---|
| `sensor.…_echo_timeouts` | state | Missing echoes, reads and writes alike, rescued or not — **the fault rate** ([ADR-013](../decisions.md#adr-013--silence-is-retried-disagreement-is-not)) |
| its `recovered` / `failures` attributes | attributes | What the retry made of them. `recovered` is what #35 is judged on |
| its `on_reads` / `on_writes` attributes | attributes | The split argued for above, now counted directly rather than inferred |
| `sensor.…_failed_polls` | state | Polls that failed after the retry, tolerated or not ([ADR-012](../decisions.md#adr-012--a-stale-reading-beats-unavailable-and-the-fix-ships-with-its-own-meter)) |

`on_reads` / `on_writes` are **counts, not rates**, and cannot become rates: the read
denominator is still unmeasurable, because a successful no-op poll writes no recorder row and
`DataUpdateCoordinator` drifts. What they can do is falsify the shared-defect claim — if a
window's timeouts land almost entirely on one side, the two populations are not one fault.

`soak.py report` prints all of them beside the rates they replace. Comparing this window's
86.4% against a later one measures the **retry**, not the link; only `echo_timeouts` compares
like with like, and a re-soak that reports zero of everything is far more likely to be a
wrong entity id than a perfect box — check `/api/states` before believing it.

**The re-soak ran 2026-08-14 → 2026-08-17 and answered all four.**
[`verification-soak-2026-08.md`](verification-soak-2026-08.md) has the results: 11
missing echoes, **11 rescued, 0 failed**, and 25/25 verified writes. #35 is proven. Note the
run used the replacement proxy board, so only `echo_timeouts` compares back to this page —
exactly the caveat above.
